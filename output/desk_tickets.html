3. What would have been simpler as one agent with tools?

  • Ticket 102, all of it. The real work is three tool calls: get_lease_due(1), request_payment('rent', 1), update_ticket_status. The team spent 13 model calls and 38k tokens on run 1 because each hand-off makes the next agent re-read the ticket, the lease and the cash. A single "ops agent" with those three tools would do it in about 4 calls with the same safety, since the money rule lives in decide_approval, not in which agent asks.
  • Every close-out run. The 101 and 102 close-outs that resolved the tickets were already effectively single-agent: the Boss alone, 4–5 calls, about 18k tokens each. "Check approvals, check the payment, mark resolved" doesn't need a team.
  • Ticket 101's first run. Inventory and Accounting both pulled invoice 501. A depth-2 Accounting run happened just to say "already pending". One agent with check_stock, get_invoice_status, create_purchase_order and request_payment would avoid that duplication and roughly halve the 60k tokens.

Where the team still earned its keep: separation of powers. Only Accounting can request payments, only the Boss can set prices or close tickets, and only Customer Service writes to customers. In a real shop that's the main protection against one confused agent doing something expensive. On 103, having one agent price it and another decide was the right structure. It just needed Accounting to bring options and a cash warning, not one number.

5. Three new problems this team could not solve, and what it would need

a) Getting paid: deposits, sales and refunds. The rules say cash only goes out, and none of my 21 tools can record money coming in. That's exactly what broke 103. If Yale AI Club paid a $435 deposit (half of $870), the shop could afford the $264 hoodie restock. Instead the team promised a restock it couldn't pay for.

Needed: a receivables table and tools like create_customer_invoice(ticket_id, amount), record_customer_payment(invoice_id, amount), which increases cash_accounts, and issue_refund, which needs human approval like any payment. Add a Billing / AR agent (or extend Accounting) that asks for deposits on orders that need a restock, and a Boss rule: "don't promise restock dates unless cash or a deposit covers the PO."

b) The physical world: receiving stock, shipping, and actually contacting people. On 101 the PO says "ETA 2026-09-05", but no tool can record the tees arriving. inventory.qty only ever goes down (fulfill_from_stock), so Tauhid's tee could never be fulfilled in this system. Every customer and vendor message is also a draft forever. There's no send step, even after a human approves it.

Needed: receive_purchase_order(po_id, qty_received) (increases inventory, closes the PO, flags a short shipment), mark_shipped(ticket_id, tracking), and an approval-gated send_message(draft_id) that only works after a human approves the draft. Add a Receiving / Logistics agent that watches open POs against vendors.lead_days and wakes Customer Service when goods land.

c) Planning across days and across tickets. The shop is frozen on desk.date_today = 2026-08-31. Nobody can notice that next rent ($2,400 on 2026-10-02) is coming while checking sits at $152 with no revenue, which is a guaranteed miss. The same blind spot caused 103's problem: no agent looks at the whole board's money before making a promise.

Needed: a forecast_cash(days) tool that projects checking from upcoming rent, open invoices and pending POs. Add an advance_day() / scheduler tool, plus a create_ticket(type, …) tool so the system can open its own reminders ("rent due in 3 days", "PO #1 overdue"). Add a Planner / Treasurer agent that runs every morning, ranks obligations, and that the Boss must consult before any quote or PO. In code: record_price_decision would refuse a quote whose restock cost exceeds the forecast cash.
